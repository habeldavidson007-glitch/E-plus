E+ v4
Language Reference

A programming language that mirrors how humans think — incremental, readable, and structured just enough to be executable. Code that reads like a thought written down.

01 Foundation

E+ v4 is no longer just an intent-first language. It is a cognitively-aligned conversational programming language that mirrors how humans think (like speech) while remaining stable and executable (like writing).

Core Realization
Humans do not think in full structured sentences, nor in symbolic syntax. They think in incremental meaning chunks — and when they write, they refine and structure those chunks. E+ v4 bridges this gap.

02 Core Model: Speech → Writing Hybrid

E+ operates on two simultaneous layers that must coexist in every valid program:

🗣
Cognitive Layer — Speech-like
Incremental. One thought at a time. Low object count (1–3 entities). Context-driven flow. Reads like explaining something aloud.
📝
Structural Layer — Writing-like
Persistent. Readable. Executable. Slightly more organized. Enables real computation and machine interpretation.
Design Mandate
The language must feel like thinking out loud, but behave like structured code.

03 Non-Negotiable Rules

Every valid E+ program must follow these constraints — they are enforced at the cognitive validator layer, not just by convention:

1
One line equals one cognitive step.
2
Each line involves at most 3 entities (agent, action, target).
3
No compressed multi-intent logic in a single line.
4
Flow must feel continuous — like explaining something step by step.
5
Symbols must not feel mechanical or repetitive; words are preferred when clearer.
Important
Rules 1–3 are enforced by the Cognitive Validator. Grammar alone does not catch violations — a semantic linter is required.

04 The E+ Dictionary

Intentionally minimal and semantically meaningful. Every element reflects how humans naturally express intent. There are no arbitrary symbols.

@
Entity Declaration — optional
Marks a named entity (thing) in your thinking. Optional in relaxed mode.
@user = < "Your name"
user = < "Your name"
<
Input — receive
Represents receiving something from outside the program. Matches the mental model: "I ask and receive."
age = < "Your age"
>
Output — express
Represents expressing or showing something to the outside world.
> "Hello, world"
?
Decision — question
Represents a question in thought. Mirrors internal reasoning: "Is this true?"
? (age > 17) → > "Allowed"
else
Fallback — natural continuation
Replaces symbolic fallback (::) with a natural continuation word. Must follow a condition block.
else → > "Denied"
→
Flow Block — continuation
Signals the continuation of thought into a block. Replaces braces and indentation rules with a single semantic arrow.
? (x) → > "yes"
repeat
Repeat — iteration
Represents iteration in natural language. Avoids symbolic loop syntax.
repeat item → > item
[ ]
Function Definition
Represents defining a reusable thought or behavior. Brackets signal a named reusable block.
[ greet ] (name) → > "Hello " + name
call / ^
Function Call — two modes
Readable mode (call) for clarity; compact mode (^) for brevity. Both are valid.
call greet("John")
^greet("John")
return / =>
Return — emit result
Readable form preferred. Emits a value from a function block.
return result
=
Assignment — state
Standard assignment; already intuitive across all programming contexts.
allowed = false
remove / ~~
Remove — discard
Deletes a named value. Readable form preferred.
remove temp
##
Comment — human layer
Human-readable annotation layer. Never affects execution.
## checking user eligibility

06 Removed Features & Why

The following were intentionally removed or discouraged from E+ v4:

@@ — mechanical repetition :: — non-natural fallback excessive symbolic operators

Rationale
These do not match how humans think or speak. They introduce artificial syntax rather than meaningful expression — and E+ v4's core mandate is alignment with human cognition, not symbolic efficiency.

07 Formal EBNF Grammar

The grammar defines syntax structure and block rules. It deliberately does not enforce cognitive constraints — those belong in the Validator layer.

08 Expression Grammar

E+ v4 deliberately does not reinvent expression grammar. It delegates to a Python-like expression model:

EBNFlogical_expr = comparison { ( "and" | "or" ) comparison } ;
comparison  = term { ( ">" | "<" | ">=" | "<=" | "==" | "!=" ) term } ;
term        = factor { ( "+" | "-" ) factor } ;
factor      = primary { ( "*" | "/" ) primary } ;
primary     = number | string | identifier | "(" expression ")" ;
Grammar vs. Philosophy
Grammar allows ? (a and b and c and d). Your philosophy forbids it. This must be caught by the Cognitive Validator with rules on max logical operators per line.

09 Block Structure

Blocks are the core structural innovation of E+. They use INDENT/DEDENT tokens (like Python), initiated by the → arrow:

EBNFblock = "→" NEWLINE INDENT { statement } DEDENT ;
program ├── assignment age = < "Age" ├── condition_stmt │ └── block │ └── output_stmt > "Allowed" └── else_stmt └── block └── output_stmt > "Denied"

10 AST Node Schema

The AST is the universal intermediate representation shared across all transpiler targets. Nodes are minimal and named after cognitive concepts:

Pythonclass Program(Node):   # root — sequence of statements
class Assignment(Node): # name = expr
class Input(Node):      # name = < "prompt"
class Output(Node):     # > expr
class Condition(Node):  # ? (expr) → block
class Else(Node):       # else → block
class Repeat(Node):     # repeat var [in iter] → block
class FunctionDef(Node):# [name] (params) → block
class FunctionCall(Node):# call name(args)
class Return(Node):     # return expr
class Remove(Node):     # remove name
class Block(Node):      # container for statement list
class Comment(Node):    # ## text

11 Lexer (Tokenizer)

The lexer converts raw E+ source text into a flat token stream. It tracks indentation to emit INDENT/DEDENT tokens, enabling block parsing without braces.

12 Token-Based Parser

A recursive-descent parser converts the token stream into an AST. It is deterministic with no regex hacks — every branch maps to exactly one grammar rule.

Key Parser Methods

MethodProduces
parse()Program node
parse_statement()Any single statement node
parse_block()Block node (expects ARROW → INDENT … DEDENT)
collect_expr()Raw expression string (pass-through to transpiler)
collect_args()List of argument strings

The Design Test

Any new feature must pass this single test before inclusion:

"Does this feel like something a human would naturally say while explaining their reasoning?"

If the answer is no — it does not belong in E+.
